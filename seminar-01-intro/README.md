## 1. Зачем нужен ещё один язык (00:00–00:10)

Go придумали в Google в 2007 году три человека — Роб Пайк, Кен Томпсон
и Роберт Гризмер — как ответ на конкретную боль: большие серверные проекты
на C++ и Java собирались десятки минут, а код был сложно читать новым людям
в команде. Go оптимизирован не под «написать покрасивее», а под
**читать и поддерживать чужой код годами**.

Отсюда три инженерных решения, которые видно с первой строки:

**Компилируется в один статический бинарник.** Никакого рантайма, виртуальной
машины и `pip install` на сервере: вы отдаёте один файл, и он запускается.
Именно поэтому на Go написаны Docker, Kubernetes, Terraform, Prometheus.

**Язык намеренно маленький.** В спецификации 25 ключевых слов
(в C++ их больше сотни). Нет наследования классов, нет исключений,
нет перегрузки операторов, нет тернарного оператора, до 2022 года не было
даже дженериков. Каждая «недостающая» вещь — осознанный отказ ради того,
чтобы код читался однозначно.

**Конкурентность встроена в язык.** `go f()` запускает горутину — это дешёвая
задача, которых можно завести сотни тысяч. Это главная причина, по которой Go
выбирают для сетевых сервисов. Мы дойдём до этого через несколько семинаров;
сегодня — фундамент.

> **Чем Go не является.** Это не замена C++ там, где нужен контроль над памятью
> и предсказуемые задержки: в Go есть сборщик мусора. Это не язык для численных
> расчётов и ML — там правит Python со своими библиотеками. Го — язык сетевых
> сервисов, инфраструктуры и утилит командной строки.

**Сравнительная таблица для ориентации:**

| | C++ | Python | Go |
|---|---|---|---|
| Типизация | статическая | динамическая | статическая, с выводом типа |
| Сборка | долгая | нет | секунды |
| Управление памятью | вручную / RAII | GC | GC |
| Ошибки | исключения | исключения | значения (`error`) |
| Наследование | есть | есть | **нет** (композиция + интерфейсы) |
| Дженерики | шаблоны | не нужны | есть с 1.18, используются редко |
| Стиль кода | предмет споров | PEP 8 | `gofmt`, споров нет |

## 2. Установка и первый запуск (00:10–00:30)

Подробная инструкция — в [`docs/setup.md`](../docs/setup.md). На паре:

```bash
go version              # проверяем, что Go в PATH
go env GOROOT GOPATH    # где лежит Go и где его рабочая папка
```

Создаём проект с нуля — **своими руками, а не копированием из репозитория**:

```bash
mkdir ~/hello-go && cd ~/hello-go
go mod init example.com/hello    # появился go.mod
```

`go mod init` создаёт файл `go.mod` — паспорт модуля:

```
module example.com/hello

go 1.24
```

Модуль — это единица версионирования и распространения кода: примерно то же,
что `package.json` в npm или `pyproject.toml` в Python. Имя модуля — это путь,
по которому его смогут импортировать другие. Для учебного проекта подойдёт любое
имя, для настоящего берут адрес репозитория: `github.com/user/project`.

Теперь `main.go`:

```go
package main

import "fmt"

func main() {
	fmt.Println("Привет, Go!")
}
```

```bash
go run .          # скомпилировать во временный файл и запустить
go build          # собрать бинарь ./hello в текущей папке
./hello
```

> **Живая демонстрация № 1.** Покажите разницу: `go run` компилирует во временный
> каталог и сразу запускает (удобно в разработке), `go build` оставляет
> исполняемый файл. Сравните со связкой `g++ main.cpp -o main` — тот же смысл,
> но без Makefile и флагов.

Разбор кода — [`examples/01-hello`](examples/01-hello/main.go).

## 3. Анатомия программы (00:30–00:45)

```go
package main    // 1
import "fmt"    // 2
func main() { } // 3
```

**1. Каждый файл начинается с `package`.** Пакет — это папка. Все файлы в одной
папке обязаны объявлять один и тот же пакет. Пакет `main` — особенный: только он
компилируется в исполняемый файл, и в нём обязана быть функция `main()`.
Любое другое имя пакета — библиотека, которую нельзя запустить, но можно
импортировать (см. [`examples/05-first-test`](examples/05-first-test/mathutil.go)).

**2. Импорты — по полному пути.** `"fmt"` — из стандартной библиотеки,
`"github.com/user/lib/pkg"` — внешняя зависимость. Импортируется **пакет**,
а не файл: аналога `#include "myfile.h"` в Go нет.

**3. Точка входа** — `func main()` в пакете `main`. Без аргументов,
без возвращаемого значения. Аргументы командной строки берутся из `os.Args`,
код выхода — `os.Exit(1)`.

### Экспорт: заглавная буква вместо `public`

```go
func Abs(x int) int   { ... }  // экспортируется: видно из других пакетов
func clamp(x int) int { ... }  // приватное: только внутри своего пакета
```

Никаких `public`/`private`/`protected`. Регистр первой буквы имени —
и есть модификатор доступа. Это относится ко всему: функциям, типам,
полям структур, константам.

### `gofmt` — конец спорам о стиле

```bash
gofmt -l .    # какие файлы отформатированы неправильно
gofmt -w .    # переформатировать
```

В Go ровно один канонический стиль, и его задаёт инструмент из поставки языка.
Табы, а не пробелы. Скобка на той же строке — иначе **не скомпилируется**
(компилятор автоматически подставляет точку с запятой в конце строки).
На код-ревью в Go никогда не обсуждают форматирование: его не существует
как темы для разговора.

```bash
go vet ./...   # статический анализатор: ищет то, что компилируется, но подозрительно
```

> **Углублённо.** Спросите: почему `{` обязана быть на той же строке?
> Ответ: лексер вставляет `;` в конце строки, если она заканчивается
> идентификатором, литералом или закрывающей скобкой. `func main()` + перевод
> строки превращается в `func main();` — и получается объявление без тела.
> Пример этой ошибки — в [`examples/03-strict-compiler`](examples/03-strict-compiler/main.go).

## 4. Инструмент `go` и что делает сборка (00:45–01:00)

Один инструмент вместо зоопарка. Сравните: в C++ вам нужны компилятор, CMake,
conan/vcpkg, clang-format, gtest. В Go всё это — подкоманды `go`.

| Команда | Что делает |
|---|---|
| `go run ./path` | Собрать и запустить |
| `go build ./path` | Собрать бинарь |
| `go test ./...` | Прогнать тесты во всех пакетах |
| `go vet ./...` | Статический анализ |
| `go mod init` / `go mod tidy` | Создать модуль / привести зависимости в порядок |
| `go doc fmt.Println` | Документация прямо в терминале |
| `go install pkg@latest` | Поставить утилиту в `$GOPATH/bin` |

`./...` — это «текущая папка и все вложенные пакеты».

> **Живая демонстрация № 2 — главная на этой паре.**
> [`examples/02-build-and-run`](examples/02-build-and-run/main.go)
>
> ```bash
> go build -o /tmp/whereami ./seminar-01-intro/examples/02-build-and-run
> ls -lh /tmp/whereami     # ~2 МБ — внутри рантайм и сборщик мусора
> /tmp/whereami            # запустится на машине без установленного Go
>
> GOOS=linux GOARCH=amd64 go build -o /tmp/whereami-linux ./seminar-01-intro/examples/02-build-and-run
> file /tmp/whereami-linux
> ```
>
> Вы только что собрали бинарь под Linux, сидя на macOS, без контейнера,
> кросс-компилятора и единого дополнительного пакета. Для человека, который
> собирал C++ под другую платформу, это самая убедительная демонстрация Go.

> **Углублённо: почему бинарь весит 2 МБ.** Внутрь вкомпилированы рантайм Go,
> планировщик горутин, сборщик мусора и таблицы для рефлексии. Взамен — нулевые
> внешние зависимости. Уменьшить можно флагами `-ldflags="-s -w"`
> (выбросить отладочные таблицы), но обычно этим не занимаются.

## 5. Компилятор-педант (01:00–01:10)

Откройте [`examples/03-strict-compiler`](examples/03-strict-compiler/main.go)
и по очереди раскомментируйте блоки. Каждый из них **ломает сборку**.

**Неиспользуемая переменная — ошибка компиляции.** Не предупреждение.
В C++ это `-Wunused-variable`, который все отключают; в Python это вообще
никого не волнует. В Go мёртвый код физически не может попасть в репозиторий.
Та же история с неиспользуемым импортом.

**Нет неявных преобразований типов.** `int + float64` не компилируется,
даже `int32 + int64` не компилируется. Пишите `float64(i) + f`.
Все привычные по C++ ловушки с сужением типов исчезают как класс.

**Условие в `if` обязано быть `bool`.** `if 1 {}` и `if ptr {}` — ошибки.
Никаких «непустая строка это истина», как в Python.

**Нет неинициализированной памяти.** Каждая переменная сразу получает нулевое
значение своего типа: `0`, `0.0`, `false`, `""`, `nil`. Чтение
неинициализированной переменной в C++ — неопределённое поведение,
в Go этого состояния просто не бывает.

> **Что за этим стоит.** Это единый принцип: язык предпочитает раннюю ошибку
> позднему сюрпризу. Компилятор берёт на себя роль ревьюера в тех вопросах,
> где ответ объективен. Из-за этого первые дни на Go раздражают, а через
> две недели вы перестаёте это замечать — и начинаете скучать по этому
> в других языках.

Быстрая экскурсия по типам — [`examples/04-types-tour`](examples/04-types-tour/main.go).
Подробно всё это разберём на семинаре 2.

## 6. Как устроен `go test` (01:10–01:20)

Тестирование в Go — часть языка, а не сторонняя библиотека. Ни pytest,
ни gtest, ни аннотаций.

Правила ровно три:

1. Файл называется `*_test.go` — он компилируется только при `go test`
   и не попадает в ваш бинарь.
2. Функция называется `TestXxx` и принимает `t *testing.T`.
3. Провал теста — это вызов `t.Errorf` (пометить и продолжить)
   или `t.Fatalf` (пометить и прервать).

```go
func TestAbs(t *testing.T) {
	if got := Abs(-3); got != 3 {
		t.Errorf("Abs(-3) = %d, ожидалось 3", got)
	}
}
```

Обратите внимание: **нет ассертов**. Вместо `assertEquals(want, got)` вы пишете
обычный `if` и сами формулируете сообщение об ошибке. Сообщение — это
не формальность: именно его вы прочитаете через полгода, когда тест упадёт.
Канонический формат: `Функция(вход) = получили, ожидалось хотели`.

Идиома, которую вы увидите во всех задачах курса, — **табличный тест**:
список случаев и один цикл по ним. Разбор — в
[`examples/05-first-test`](examples/05-first-test/mathutil_test.go).

```bash
go test ./seminar-01-intro/examples/05-first-test
go test -v ./seminar-01-intro/examples/05-first-test
```

## Вопросы, которые задают почти всегда

**«Почему нет исключений?»**
Потому что исключение — это невидимый путь выполнения. В Go ошибка — обычное
значение, которое функция возвращает вторым результатом, и его нельзя
проигнорировать молча. Ценой становится многословность: `if err != nil` вы
напишете тысячу раз. Разберём подробно на семинаре про ошибки.

**«Почему нет классов и наследования?»**
Есть структуры с методами и интерфейсы. Наследования реализации нет сознательно:
опыт больших кодовых баз показал, что глубокие иерархии классов ломают
читаемость. Вместо «является» используется «содержит» — композиция.

**«Дженерики есть?»**
Есть с версии 1.18. Но в Go их применяют заметно реже, чем шаблоны в C++:
сначала пишут конкретный тип и обобщают, только когда дублирование стало реальной
проблемой.

**«Насколько Go быстрее Python?»**
На вычислительных задачах — обычно в десятки раз. Но выбирают Go не поэтому,
а из-за конкурентности, статической типизации и одного бинарника при деплое.

**«Где смотреть документацию?»**
<https://pkg.go.dev> — вся стандартная библиотека и все публичные пакеты.
В терминале то же самое: `go doc strings.Builder`.
Интерактивный тур — <https://go.dev/tour/> (можно пройти за вечер).
